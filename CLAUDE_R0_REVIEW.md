BEFORE_AFTER_CONTRACT=Four mechanisms. (1) **Identical input**: fixture is seed-derived and its checksum is written into the artifact; a run whose checksum differs from the baseline's fails rather than reporting an incomparable delta. (2) **Identical instrument**: the artifact carries a `harnessVersion`; changing `fake-postgrest.ts` (e.g. adding `count` support for R2A) bumps it, and a version mismatch forces you to **re-run BEFORE on the extended fake** before comparing. Today the harness must duplicate the page's `Promise.all`; a duplicated block silently stops mirroring the page the moment R2A edits it. Targeting a shared symbol makes drift a compile error. LIMITATIONS=
- **No planner, no indexes, no network.** In-process wall time is essentially JS mapping cost. Treat round trips, rows and bytes as the proof; treat modeled latency as a stated model with recorded constants, not a measurement. If R2 ever includes an index or an RPC, this harness cannot score it and you need option 3 or 4 for that piece specifically.
- **The fake's operator coverage is partial.** `or()` handles only `in` and `eq` terms (`matchesOrTerm`, line 107) â€” sufficient for `getApplications`' current `season_id.in.(â€¦),intake_batch_id.in.(â€¦)`, but if R2A adds `ilike` search or `textSearch` it must be extended. Failure is loud (a thrown `unsupported or() term`, or an undefined builder method), never a silently wrong number â€” which is the property that makes this acceptable.
- **`count`/`head` are unmodeled today.** Called out above; must land before the R2A "after" run.
- **It measures the data layer, not the page.** React render, serialization and network transfer to the browser are excluded. Since R2A/R2B change only data access, this bounds the improvement from below â€” the real user-visible win should be at least what this reports.
- **Row-count realism is asserted, not sampled from Production.** 1,500 applications and the related-table volumes are the specified target, not a measured production distribution; if real season shape differs materially the absolute numbers shift, though the before/after ratio is robust to that.
- **Fixture fidelity to the real schema is unverified by construction** â€” the fake has no DDL, so a column that doesn't exist in Production would go unnoticed. Mitigation is the optional option-4 cross-check: run `scripts/benchmark-application-scale.mts --measure-only` against a non-prod project once and confirm the request counts per table agree with the harness. Confirming counts agree upgrades this from "plausible model" to "validated model"; it is worth doing once, but R0 does not block on it.
